I wanted to keep working on my Mac from the iPad upstairs, so an AI built Mac Remote

The story of Mac Remote, an iPad app that controls your Mac over VNC, built with Claude Code. A black screen, a 38-second login and a tap bug, with my real prompts.

By 9M4ck · Beginner

This one started with a two-storey house. I leave my MacBook on the first floor with a terminal job still running, but I'm upstairs with an iPad next to me. I just wanted to carry on working without walking down every time.

So I told Claude Code, plainly, that I wanted an iPad app that remotes into my Mac on the same network. I didn't pick the technology and I didn't write any code. The result is Mac Remote.

No download link yet. I searched the App Store and this app isn't there, and the code sits in a private GitHub repo. So this post is just the story. If it ever reaches the store, I'll add the link.

Day one: from one sentence to an app that builds

My first prompt came at 15:02 on 17 October and was very short (it's at the end of this post). Within about ten minutes Claude had checked my machine, seen that macOS Screen Sharing was already on, picked a VNC library called RoyalVNCKit and written a SwiftUI app. It built, and in the simulator it found my MacBook on the network by itself. At 15:14 it reported it was done.

Then I tried it on the real iPad, and it wasn't.

Bug 1: a black screen (and one wrong answer first)

I typed, "now it run on ipad but it black screen". Claude's first guess was that my Mac sends every pixel with a spare fourth byte set to 0, which the library treats as transparency, so the picture was see-through. It rebuilt the image itself and ignored that byte. The screen was still black, and Xcode showed it as paused with a wall of assembly, which I simply pasted back.

From the line __abort_with_payload inside dyld it concluded this wasn't a drawing problem at all. The app crashed at launch because the system couldn't load the RoyalVNCKit library, which had never been copied into the app. The fix was one line, embed: true, in project.yml. After that the app stayed open for 6 seconds or more, where before it died at once. I'd asked for an icon in the same message: a white laptop with a green >_ prompt and a green Wi-Fi badge on blue, drawn by a Swift script.

What I took from this The first explanation sounded reasonable and was wrong. What actually helped was pasting the real log from Xcode instead of describing the symptom in words.

Bug 2: connecting took forever

The screen appeared, but I asked, "i connecting for a long time but it can connect in finally, is it normal?" Claude said no, it should take 1 to 3 seconds. It put timers into the app and read the results from the log:

  • Finding the Mac: 0.16 seconds
  • Opening the connection and reaching sign-in: 0.8 seconds
  • From sign-in to the first picture: 38 seconds

The cause: signing in with a Mac username and password uses a 4096-bit key exchange. The library does that maths in plain Swift, and Xcode's Run button was building in Debug mode with no optimisation. On the Mac, Claude measured about 26 seconds in Debug against 0.8 seconds in Release. I would never have guessed that. The fix was to make the Run button build Release in project.yml.

Bug 3: tapping opened a right-click menu

Another message I sent: "when i tab on ipad it not click but it show menu like a right click from mouse". The cause was a feature the AI had added on its own to support a real mouse: a tap recogniser meant to accept only the right mouse button. iOS ignores that filter for finger taps, so it fired on every tap and beat the normal click. It was changed to accept only a real mouse.

At the end of that session Claude installed the build and said plainly that it hadn't confirmed the speed or tap fixes itself, because getting past sign-in needs my password, which I don't give it. The testing on the iPad was left to me. My records stop at that point, so I won't claim that everything was perfect afterwards.

Can I use it away from home?

The next morning (18 October) I asked, "can it connect to mac over internet". The answer was Tailscale, which makes a private, encrypted network between your own devices. The app needs no changes: you add a second entry using the Mac's address on that network. The caveats it gave me:

  • Automatic discovery only works on the same Wi-Fi, so keep two entries: the one the app finds itself, and one for when you're away
  • Tailscale must stay running on the Mac, and the Mac must stay awake
  • Don't forward port 5900 on your router. That puts your Mac's login screen on the open internet for password-guessing bots
  • My screen is 2560×1664 sent in full colour. Fine at home, but it can lag on mobile data. It offered to add a low-bandwidth mode, but I didn't ask for it, so it isn't there

How it feels to use

From the project's README: trackpad mode is the default. Drag one finger to move the pointer, tap to click, two-finger tap to right-click, two-finger drag to scroll, pinch to zoom. The on-screen keyboard gets an extra row with esc, tab, sticky ⌃ ⌥ ⌘ ⇧, arrows and ⌃C, which matters a lot to someone who lives in the terminal.

Made with AI. All the code was written by Claude Code. I said what I wanted, tested it on my own iPad, and said what was wrong. This post uses a banner made from the app icon rather than screenshots, because a remote screen would show my real Mac.

If you try this Turn on Screen Sharing only on a network you trust. Never type your password into an AI chat; enter it in the app's own settings screen. If you want it away from home, use a private network such as Tailscale instead of opening a port on your router.
